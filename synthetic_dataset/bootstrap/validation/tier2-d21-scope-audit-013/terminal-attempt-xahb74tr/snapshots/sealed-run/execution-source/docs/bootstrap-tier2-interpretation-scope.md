# Specification-first separation of program requirements and workflow context

The fresh stage 010 D21 run ended BLOCKED before Lean acceptance. Its interpreter
introduced O8, a required guarantee about preserving contract metadata, checking
reconstructed facets at three workflow stages, and the configured trust boundary.
All fifteen O8 citations lie in appended bootstrap scaffolding, beyond the
preserved software request and examples. O8 is absent from the eleven original
identities and the nine requested source-policy rows. The subsequent formalizers
reported the same concrete capability gap: the implementation language cannot
inspect an actual CLI run or prove its checker configuration from aggregation
inputs. The failed run and its exact responses remain immutable.

The aggregation behavior and its original source guarantees remain required.
This milestone corrects how the bootstrap publishes requirements; it does not
extend program semantics with an invented predicate for workflow observations.

## Requirement ownership

The revised software request contains the original functional clauses and public
examples, the explicit canonical VSCore delivery revision, stable requirement
identity metadata, and the same per-ID program source requirements. Every original
kind, role, required flag, domain and applicable value facet remains mandatory.
Only the previously declared operational IDs are source-only.

Instructions about the CLI's own proof, staged checking, review, endpoint
selection and trust configuration belong to supervisor workflow context. Publish
that context in a named, hash-bound field of the delivery-revision sidecar, which
is already a preregistered input. Retain the actual configuration, source policy,
registered checking stages and closure claims unchanged. Context text describes
requirements of the run and never establishes their satisfaction.

The program request must not state that solve verifies its own contract registry,
staged checking events or host configuration. Explicit requests to implement a
verifier, audit log or metadata-processing program remain software requirements;
this separation does not authorize classifying those requested behaviors as
context or removing unsupported user requirements.

Native interpreter guidance must distinguish supervisor-provided instructions
about this run from the behavior of the user's requested implementation. Context
clauses still require ledger coverage and explanatory notes. Requested program
source properties, functional safety, invariants, branches, examples and complete
input/output behavior remain obligations with source citations.

## Required implementation and qualification

1. Split the bootstrap's generated program requirements from its generated
   workflow commentary. Bind the latter to exact UTF-8 bytes and a digest in the
   delivery-revision input. Preserve all original functional bytes and examples,
   the identity mapping, and the exact required-source-policy digest.
2. Add general native interpreter guidance for supervisor workflow context,
   without special-casing D21, deleting a retained obligation, or inventing proof
   evidence. The current failed package cannot be edited or rescored.
3. Verify the separation with unrelated public software clauses that themselves
   request artifact checking, plus the existing preservation, source-policy,
   frozen-provider-context and actual native source/closure tests. Preserve every
   trial result and bind test files independently of the execution-source freeze.
4. Freeze the changed generic sources before a new fresh D21 run. Require an
   unrelated actual two-build engineering fixture and no task-model calls in its
   qualification. Do not reuse a historical task source, proof or positive case.
5. Run the normal strict CLI from the revised natural-language request with fresh
   stateless model roles and native repair loops. Store JSON, Lean, diagnostics,
   review and bridge artifacts. Audit natural-language correspondence, accepted
   reconstruction, universal source refinement, all required claims, reviews and
   both seals. Report the result at Tier 2 / restricted_source; optional TESTED
   remains pending and Python/compiler/machine-code assurance remains excluded.

Success requires a newly sealed VERIFIED D21 run with its original functional
requirements and all applicable implementation guarantees proved through the
actual source bridge. A prompt correction or mock test alone is not success.
