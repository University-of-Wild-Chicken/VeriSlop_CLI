# Provider adapter source references

Research date: 2026-10-05. These are official documentation references for proposed adapter designs. Runtime support requires pinned adapter versions and conformance tests. Model names, service access, API versions, region availability, and authentication profiles must be resolved for the user's account before dispatch.

- **OpenAI (`openai`)**: Responses is the native API family for the proposed adapter. Use the documented bearer-credential profile and keep credentials in the provider broker. [API overview](https://developers.openai.com/api/reference/overview), [Responses reference](https://developers.openai.com/api/reference/responses/overview).
- **Claude / Anthropic (`anthropic`)**: Use the native Messages protocol with its documented authentication and API-version header. Configure cloud-hosted Claude separately from the direct API. [API overview](https://platform.claude.com/docs/en/api/overview), [authentication](https://platform.claude.com/docs/en/manage-claude/authentication).
- **Gemini / Google (`google_gemini`)**: The Gemini Developer API uses its API-key authentication and native content-generation protocol. Vertex AI is a separate service/authentication profile. [Gemini API reference](https://ai.google.dev/api), [content generation](https://ai.google.dev/api/generate-content).
- **DeepSeek (`deepseek`)**: Supports an OpenAI-compatible chat API; select and pin the protocol family because additional compatibility surfaces exist. [Official API documentation](https://api-docs.deepseek.com/), [integration guide](https://api-docs.deepseek.com/guides/codex).
- **Qwen / Alibaba Model Studio (`alibaba_model_studio`)**: The OpenAI-compatible DashScope surface uses bearer API credentials. Base URL, workspace, region, and service plan must match the key. [OpenAI compatibility](https://www.alibabacloud.com/help/en/model-studio/compatibility-of-openai-with-dashscope), [endpoint selection](https://www.alibabacloud.com/help/en/model-studio/base-url).
- **GLM / Z.AI (`zai`)**: The documented general API uses bearer authentication and a chat-completions endpoint. Coding-plan and other deployment profiles must use their documented endpoints rather than assuming the general endpoint applies. Zhipu deployments are distinct registry profiles. [API introduction](https://docs.z.ai/api-reference/introduction).
- **Kimi / Moonshot (`moonshot`)**: The documented chat-completions API uses an OpenAI-compatible surface and bearer credentials. Explicitly declare the chosen API family. [Official chat API](https://platform.kimi.ai/docs/api/chat).
- **Grok / xAI (`xai`)**: The inference API supports Responses and Chat Completions with bearer credentials. Inference credentials are distinct from management credentials. [Inference reference](https://docs.x.ai/developers/rest-api-reference/inference).
- **Muse / Meta (`meta`)**: This design interprets Muse as Meta Muse Spark through Meta Model API. Its documentation describes Responses, compatible Chat Completions, and Messages surfaces with bearer credentials. If the user means a different Muse service, require an explicit provider/endpoint profile. [Meta Model API overview](https://dev.meta.ai/docs/overview).

The adapter interface abstracts transport, authentication, streaming, tool calls, response validation, usage reporting, cancellation, and errors. It does not assume that services sharing a protocol name share every behavior or model capability.
